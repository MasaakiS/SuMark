# SuMark コメントポリシー

このドキュメントは、ソースコードコメントの品質を一定に保つための基準です。
対象は `src/`, `src-tauri/`, `docs/` のすべてのコードです。

## 目的

- 可読性を上げる（なぜその実装かがわかる）
- 古い情報を減らす（移行メモや履歴の放置を防ぐ）
- 仕様制約を守る（Markdown変換、テーブル制約、サニタイズ）

## 基本原則

1. コメントは「何をしているか」より「なぜ必要か」を優先する。
2. コードから自明な説明は書かない。
3. 実装と同期しないコメントは残さない。
4. 履歴はコード内ではなく`CHANGELOG.md`やPRに残す。
5. 1コメント1意図を基本に、長文説明はdocsに移す。

## 言語方針

- デフォルトは日本語。
- 識別子、ライブラリ名、ログタグ（`DEBUG` など）は英語を維持する。
- 英語コメントを残す場合は、プロトコル名や仕様名など固有語に限定する。
- 同一ブロック内で日英が混在する場合は、どちらかに統一する。

## 残すべきコメント

- 複雑なロジックの意図やアルゴリズムの考え方
  - 例: なぜその手順で処理するか、境界条件をどう扱うか、計算量や順序に意味がある理由
- 挙動制約の理由
  - 例: テーブルセル内でブロック要素挿入を制限する理由
- 変換ロジックの前提
  - 例: Markdown↔HTMLのroundtripで壊れやすい仕様
- 単純化しない実装の理由
  - 例: 互換性維持、ブラウザ差異回避、既存データ保護、回帰防止のための意図的な実装
- セキュリティ上の意図
  - 例: `escapeHtml`、サニタイズ、URL検証
- 互換性の事情
  - 例: Notionエクスポート前処理、OS依存パス処理

## 削除または移動するコメント

- 「〜は別モジュールへ移動済み」の履歴メモ
- 関数名を言い換えただけの説明
- 同一内容の重複コメント（ファイルヘッダーと関数内の二重記載）
- 永続化されている一時デバッグメモ

## 書き方ルール

- 1行目で要点、必要なら次行で条件や副作用を書く。
- 40〜80文字程度の短い文を推奨。
- 箇条書きは最大3項目程度に抑える。
- 複雑ロジックには「意図」「選択理由」「壊れる条件」を最低1つずつ明記する。
- 不自然に見える実装には「なぜ単純化しないか」を1文で残す。
- TODOは期限または条件を付ける。
  - 例: `TODO(v0.7): ...` / `TODO(after #123): ...`

## 重点領域（変更時に要注意）

- `src/modules/markdown.js`
  - 変換仕様の意図コメントを削りすぎない。
- `src/modules/autoConvert.js`
  - 自動変換の境界条件（IME、空白、記号）を明示する。
- `src/modules/tableManager.js`, `src/modules/toolbarActions.js`
  - `closest('td, th')` 由来の制約理由を維持する。
- `src/modules/fileManager.js`
  - パス正規化・相対解決の互換性理由を残す。
- `src-tauri/src/main.rs`
  - ウィンドウクローズ経路の差分理由を簡潔に残す。

## レビュー時チェックリスト

- コメントが現在のコード挙動と一致しているか。
- 削除したコメントの情報が実際に不要か。
- 追加したコメントが実装の意図を増やしているか。
- 仕様制約コメント（変換・テーブル・サニタイズ）を失っていないか。
- 日英方針がブロック単位で守られているか。

## 推奨確認コマンド

```bash
npm run test:lint
npm run test:e2e -- test/playwright/08-roundtrip.spec.js
npm run test:e2e -- test/playwright/04-table.spec.js
```

必要に応じて `npm run test:e2e` を実行し、全体回帰を確認してください。
